# 4-7 Test Infrastructure and the Coverage Pipeline

> What this solves: how this repository's tests run, where the coverage reports come from (`test_coveragedumps/`, `test_reports/`), how multiple PHP versions are verified, and what the few generator scripts do.
> Prerequisites: [Chapter 2-17 Testing](testing.md) (writing tests for your application); this chapter covers **the framework repository's own pipeline**. About 20 minutes.
> Related: `docs/zh/reference-maintenance-guide.md` §5 (the full commands of the coverage-and-documentation consistency flow).

```bash
# run all commands below from the repository root
# daily: run a single test file only (a full run is slow, see below)
wsl -e bash -lc "php vendor/bin/phpunit --no-coverage tests/Core/AppTest.php"
# full run (about 5~6 minutes; prints Test Lines and the report path at the end)
wsl -e bash -lc "php vendor/bin/phpunit --no-coverage"
```

## Minimal example

The real tail of a full run (measured):

```
 All Done  Test Done!
Test Lines: 4815/4815(100.00%)
Time: 05:37.255, Memory: 14.00 MB
OK (92 tests, 556 assertions)
```

- `Test Lines: 4815/4815` comes from `dvaknheo/libcoverage` (this repository's coverage component) and means **all test code lines** were executed;
- the report file: `test_reports/index.html` (plus `test_reports/dashboard.html`);
- per-class dumps: `test_coveragedumps/<ClassName>.php` (e.g. `test_coveragedumps/Core/App.php`).

## How it works

### 1. A pipeline assembled from three pieces

```
phpunit.xml                 → 测试套件定义（bootstrap、testsuite、覆盖率收集范围）  # test suite definition (bootstrap, testsuite, coverage collection scope)
tests/bootstrap.php         → 自动加载 + LibCoverage 初始化（喂 tests/data_for_tests/setting.php 的选项）  # autoloading + LibCoverage initialization (fed the options of tests/data_for_tests/setting.php)
测试里的 Begin/End          → 每个测试自己声明"我在测哪个类"  # Begin/End in tests: each test declares "which class I am testing" itself
tests/support.php           → CodeCovar 套件：汇总生成整份报告  # the CodeCovar suite: aggregates everything into the full report
```

Two key settings in `phpunit.xml`:

- `<testsuite>` points at the whole `./tests/` (plus a `CodeCovar` suite pointing at `tests/support.php`);
- `<coverage><include><directory>./src/</directory>` — coverage **counts only `src/`** (`tests/` itself is not part of the coverage denominator);
- `processIsolation="true"`: each test file runs in its own process (clean isolation, at the cost of speed);
- `convertNoticesToExceptions` / `convertWarningsToExceptions`: **a notice/warning counts as a failure**.

### 2. How coverage is produced

```php
// the head/tail of every test file (repository convention)
\LibCoverage\LibCoverage::Begin(MyClass::class);
// ...exercise the code under test...
\LibCoverage\LibCoverage::End();
```

- `LibCoverage` is a **standalone component** (`dvaknheo/libcoverage` on composer) that can count "was this line executed" without xdebug;
- `tests/bootstrap.php` initializes it with the options of `tests/data_for_tests/setting.php` and defines the `MyLibCoverage` subclass (which adds a "clean the test database" hook, `cleanTestDb()`);
- the HTML report is generated by `LibCoverage::G()->showAllReport()` in `tests/support.php`; it only **aggregates**, so the individual tests must first produce their dumps.

**When you want real xdebug line coverage**, the environment variable must be set from outside:

```bash
XDEBUG_MODE=coverage php vendor/bin/phpunit tests/Ext/PermissionMenuTest.php
```

> Why it cannot be set in `phpunit.xml`/`ini_set`: `xdebug.mode` is `PHP_INI_SYSTEM` and cannot be changed at runtime under PHP 8+ (especially 8.4) — the `ini_set` line in `tests/support.php` only works on PHP < 8, and its comment says so.

### 3. The real semantics of `@codeCoverageIgnore` (a pit already stepped into)

- php-code-coverage only accepts a comment that is **exactly** `// @codeCoverageIgnore` and nothing else;
- it ignores **the line the comment sits on** — so paste it at the **end of the line** of `catch (...)` / `return`; it must not occupy a line of its own;
- to ignore a range, use `// @codeCoverageIgnoreStart` … `// @codeCoverageIgnoreEnd`.

### 4. Multiple PHP versions and containers

| Asset | Content |
|---|---|
| `docker/docker-compose.yml` | Top-level orchestration |
| `docker/test-php74/` | PHP 7.4 Dockerfile + compose (**there is no `.sh` script in this directory**) |
| `docker/test-php84/` | PHP 8.4 Dockerfile + compose, aligned line by line with the 7.4 one (likewise no `.sh` scripts) |

Both directories are used the same way: `cd docker/test-phpXX && docker-compose run --rm fulltest`. It mounts the whole repository at `/DATA`, starts a password-protected redis, runs `rm -f composer.lock && composer update` (using **the root `composer.json`**, resolving dependencies for the current PHP version), then runs the full `vendor/bin/phpunit`; `XDEBUG_MODE=coverage` is already set, and the coverage dumps plus the `test_reports/` aggregation are mounted back into the directory.

The 8.4 one differs from 7.4 in exactly one spelling: the last step is `vendor/bin/phpunit`, not `composer exec phpunit` — Composer 2.8 shipped in the php84 image **has removed the `exec` subcommand** (Composer 2.2 in the php74 image still has it).

The point of containerization: the **redis extension** and the syntax differences between PHP versions (this framework supports `>=7.4`) must be verified in real environments. Running on the Windows side gives false failures on the redis-related test cases (see [Chapter 2-17](testing.md) for details). Both containers currently complete the full run: **`OK (95 tests, 875 assertions)`, coverage `4735/4735 (100.00%)`**, consistent with the WSL baseline.

### 5. Generator and gate scripts

| Script | Purpose |
|---|---|
| `docs/scripts/gen-reference.php` | Reference-manual tool: `facts` (print source-parsing results), `skeleton` (generate a documentation skeleton), `verify` (compare methods/options) |
| `docs/scripts/gen-route.php` | Minimal skeleton generation (in the [Route](../reference/Core-Route.md) style) |
| `docs/scripts/gen-options-docs.php` | Generate the options documentation (`options*.md`) from source |
| `docs/scripts/scan-options.py` | Scan `$options`/`$hidden_options`, reporting keys that are "read but not declared" and spelling variants |
| `tests/genoptions.php` | Generate option-related verification data (the composer script `genoptions`) |
| `docs/scripts/check-doc-links.py` | In-site md link check (0 broken links is a hard requirement of this repository) |
| `docs/scripts/find-unmentioned-classes.py` | Reverse-lookup of the guide's reference-page links: reports class pages "never linked from the guide" (`--all` also lists those linked only once) |
| `docs/scripts/check-non-ascii.sh` | Pure-ASCII check for `src/` (must run after touching `src/`) |

> These scripts all live under **`docs/scripts/`** and are committed together with the docs: they serve only documentation generation and verification (they are not part of the framework runtime), and keeping them in `docs/` lets "documentation change + generator change" land in the same commit, in the same place. All commands run from **the repository root** (e.g. `python3 docs/scripts/check-doc-links.py docs/zh`).

`composer run-script fulltest` (in the 8.4 container/environment) chains **php-cs-fixer → phpstan → phpunit → genoptions** — the most complete pre-commit gate.

> ⚠️ `gen-reference.php verify` **misses methods** in big files that `use Trait { … as … }` and override (e.g. `Core/App.php`), and then falsely reports correct documentation as "has extra methods". Judge consistency by the drift-scan script (see `reference-maintenance-guide.md` §5).

## Common patterns

**① Run only the piece you changed**

```bash
wsl -e bash -lc "php vendor/bin/phpunit --no-coverage tests/Ext/MyMiddlewareManagerTest.php"
```

**② After a run, look at one class's coverage dump**

```bash
ls -la test_coveragedumps/Core/ | head          # one php file per class
# report: test_reports/index.html (open in a browser)
```

**③ Rebuild only the report (without rerunning all tests)**

```bash
php vendor/bin/phpunit tests/support.php        # the CodeCovar suite: aggregates the existing dumps
```

**④ The three self-checks after editing docs**

```bash
python3 docs/scripts/check-doc-links.py docs/zh      # expect broken: 0
bash docs/scripts/check-non-ascii.sh                 # after touching src/, expect Total non-ASCII lines: 0
python3 docs/scripts/scan-options.py                 # option-table-related checks
```

**⑤ The full pre-commit gate (8.4 environment)**

```bash
composer run-script fulltest
```

## Common errors

| Symptom                                      | Cause                                                                | Fix                                                                                       |
| --------------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Tests on Windows report `Class 'Redis' not found` | Windows PHP has no redis extension                                            | Always run in WSL / a container ([Chapter 2-17](testing.md))                                                     |
| Coverage numbers are all 0                               | `XDEBUG_MODE=coverage` is not set, or you ran with `--no-coverage` and never ran the `CodeCovar` suite | See §2; a report needs the two steps dump + `showAllReport()`                                                    |
| `@codeCoverageIgnore` has no effect               | The comment is not exactly the whole line, or it is not pasted at the end of the target line                                                 | Paste it at the end of the target line (§3)                                                                               |
| The full test run fails occasionally                                | `ZAllDemoTest` starts a built-in server on the fixed port 9802, conflicting with other instances/leftover processes                      | Make sure nothing runs in parallel; switch to sequential execution if necessary                                                                        |
| After changing `src/`, `ZAllDemoTest`'s `files` goes red | It compares output **byte lengths** (including the option table and the method table)                                          | Update the corresponding expectations in `tests/data_for_tests/ZAllDemoTest.config.php` (dumps are stored as `ZAllDemoTest-<length>.txt`) |
| `gen-reference.php verify` reports "extra methods"      | Trait-alias overrides in big files make the script miss methods (known defect)                                | Judge by the drift scan; do not delete documentation accordingly                                                                          |
| Wanting to run commands manually inside a container (things like `start-docker.sh` not found under php74)  | That set of start/stop scripts (the four `.sh` that existed only in the php84 directory) **has been deleted**; both directories now use only `docker-compose`                 | Enter the container with `docker-compose run --rm fulltest sh`, or run a single command with `docker-compose run --rm fulltest <command>`                             |
| `tests/support.php` won't run                | No test has run yet (there are no dumps to aggregate), or bootstrap failed                               | Run at least one test file first                                                                               |
