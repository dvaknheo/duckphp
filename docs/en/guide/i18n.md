# 2-15 i18n and Wording

> What this solves: letting the application display wording in the visitor's language — automatic language detection, translation lookup by key, `{name}` placeholders, and `[[key|fallback]]` placeholder translation.
> Prerequisites: [Chapter 1-5 Configuration and Settings](configuration.md), [Chapter 2-6 Views and Templates](views.md). About 15 minutes.
> Example: `demo/view/main.php` has one line of real usage, `<?= __l("hello")?>` (that's all there is on the view side). `demo/` has **no** accompanying language files and no complete i18n demo page — so the language-file part of this chapter describes a **convention** (the project creates `config/lang-<locale>.php` itself per the convention), and code segments marked "illustrative" are pattern demonstrations.

## Minimal example

`demo/view/main.php` (a real file):

```php
<h1>Hello DuckPhp T: <?= __l("hello")?></h1>
```

Language files live at `config/lang-<locale>.php` by convention (the following is **illustrative** — create it in your own project; `demo/` doesn't have this file):

```php
// the MyProj project's config/lang-zh_CN.php
return [
    'hello'   => '你好',
    'welcome' => '欢迎, {name}!',
    // …
];
```

So: when the request carries `?lang=zh_CN`, `__l("hello")` outputs the translation of the `hello` entry from the sample above; **when there is no language file (or this key is missing), it falls back to the original string** — the page shows `hello`. That is also the first place to look when troubleshooting "the translation didn't take effect".

## How it works

### Entry: `__l()` → `CoreHelper::_L()` → `App::lang()` → `Lang::language()`

The call chain (all verifiable by grep):

1. The global function `__l($str, $args = [], $fallback = null)` (`src/Core/Functions.php` lines 15–18);
2. [`CoreHelper::_L()`](../reference/Core-CoreHelper.md) calls `App::_()->lang($str, $args, $fallback)` (`src/Core/CoreHelper.php` lines 144–147);
3. [`DuckPhp::lang()`](../reference/DuckPhp.md) overrides `App::lang()`: if the `lang_handler` option is set it calls that directly; otherwise it calls [`Lang::_()->language(...)`](../reference/Component-Lang.md) (`src/DuckPhp.php` lines 205–213).

> Note: the `Helper` traits ([App](../reference/Core-App.md)/Business/Controller/Model) have **no** `Lang()` static method. In views use the global functions `__l()` / `__hl()` / `__langtext()`; in PHP code use `App::_()->lang(...)` or `Lang::_()->language(...)` directly.

### The five levels of language detection

`Lang::detectLanguage()` (`src/Component/Lang.php` lines 232–251) tries the entries of the `lang_detect_mode` array **in order** and returns the first non-null result:

| Order | Source | Option | Description |
|---|---|---|---|
| 1 | URL parameter | `lang_url_param` (default `'lang'`) | `?lang=zh_CN` |
| 2 | Cookie | `lang_cookie_name` (default `'lang'`) | |
| 3 | HTTP header | — | Parses `Accept-Language`, taking the first in descending `q` value |
| 4 | CLI environment variables | — | Reads `LANG` / `LC_ALL` / `LC_MESSAGES` / `LANGUAGE` in turn, stripping the `.UTF-8` suffix |
| 5 | Default value | `lang_default` | Fallback |

All results are normalized by `normalizeLocale()`: `zh-cn` / `zh_cn` / `zh-CN` all become `zh_CN` (language lowercase, region uppercase, separator unified to underscore).

**Short-circuit rule**: once the `lang_final` option has been computed at init (or you configured it directly), later requests don't re-detect. `lang_follow_root` (default `true`) makes child apps directly adopt the root app's `lang_final` without detecting on their own.

### Translation file directory convention

By default it reads from `config/lang-<locale>.php`: the `lang_file_path` option defaults to `'lang-'`, and [`Configer`](../reference/Component-Configer.md) assembles it into `{path_config}/lang-{locale}.php`, e.g. `config/lang-zh_CN.php`. The file returns a key→sentence associative array; values may contain `{name}` placeholders.

If an old project uses the "directory + locale filename" layout like `config/lang/zh_CN.php`, set `lang_file_path` back to `'lang/'` and it keeps running as before.

**frag: extra translation files for extensions.** The filename is `{lang_file_path}{locale}-{frag}.php`, e.g. `config/lang-zh_CN-for_myext1.php`. Two ways of adding:

```php
// 1) add them all at once in configuration
'lang_frags' => ['for_myext1', 'for_myext2'],

// 2) add in code (an extension does this in its own init(); the second argument is its built-in sentences)
Lang::_()->loadLanguageFrag('for_myext1', ['myext1.title' => 'My Ext']);
```

Merge rules: for the same key **the main file wins**; among frags **the later-loaded wins**; a missing frag file is treated as absent, no error. The framework's own [`RouteHookWebInstaller`](../reference/Ext-RouteHookWebInstaller.md) configures the installer page's wording per language exactly this way (`config/lang-zh_CN-for_webinstaller.php`).

You can also **skip files entirely**: write the sentences directly in the option `lang_simple_mode_only_sentences` (shaped like `['zh_CN' => ['hello' => '...']]`, one sub-array per locale), suitable for filesystem-less scenarios. Note this is "simple mode": once on, **not a single file is read**, frags stop working too, and only the default sentence set remains effective.

### Placeholder translation and the fallback chain

The lookup order of `Lang::language($str, $args, $fallback)` (`src/Component/Lang.php` lines 160–179; sentence-table merging at lines 142–159):

1. Look for `$str` in the main language file for the current `lang_final` plus each frag (main file first);
2. Not found → check the default sentence set injected via `importDefaultSentences()` / `loadLanguageFrag()`;
3. Still not found → use `$fallback` (if the caller passed one);
4. No `$fallback` passed → **return `$str` as-is**; whether to log is decided by `lang_warn_on_missing`, default **off** (when on, it writes a `No Language sentence Dectected ...` warning).

`{name}` placeholders are string-replaced after a translation is hit; **on a miss, no replacement is done on the original string** (no effect in contexts where the original string has no `{name}`).

`replaceText()` / `__langtext()` support embedding `[[key|fallback]]` placeholders **inside a piece of text**: `Lang::_()->replaceText('Use [[command.foo|foo]] mode')` replaces `[[command.foo|foo]]` with the translation of `command.foo` (or `foo` when missing).

### `lang_handler`: take over translation completely

Once `'lang_handler' => callable` is set, `App::lang()` calls it directly and **no longer goes through the `Lang` component**. Suitable for plugging in an external translation service or your own key mapping. There is a real test case at line 107 of `tests/DuckPhpTest.php`.

## Common patterns

```php
// 1) Translate in views (the most common)
<h1><?= __l('welcome', ['name' => $user['name']]) ?></h1>
<?= __hl('welcome', ['name' => $user['name']]) ?>   <!-- 翻译 + HTML 转义 -->

// 2) Translate in PHP code
$msg = App::_()->lang('welcome', ['name' => 'Duck']);

// 3) Placeholder translation: embed keys in a whole piece of text
$text = __langtext('Use [[command.foo|foo]] mode');
// if command.foo has a translation it is replaced; otherwise the fallback "foo" is shown

// 4) Specify a fallback (shown when the language file misses, instead of the original key)
$label = __l('custom_label', [], '自定义标签');

// 5) Inject default sentences (a fallback when language files can't be loaded)
Lang::_()->importDefaultSentences(['webinstaller.h1' => 'DuckPhp Web Installer']);

// 6) An extension attaches its own translation file: config/lang-zh_CN-for_myext1.php
Lang::_()->loadLanguageFrag('for_myext1');
// or add them all at once in configuration: 'lang_frags' => ['for_myext1', 'for_myext2']

// 7) To log missing sentences (off by default), turn on the switch
'lang_warn_on_missing' => true,

// 8) Custom language detection (illustrative: there is no ready-made example project in the repository)
class App extends DuckPhp
{
    public $options = [
        'lang_default'     => 'zh_CN',
        'lang_detect_mode' => ['url', 'cookie', 'default'],  // skip header / cli
    ];
}
```

## Common errors

| Symptom | Cause | Fix |
| --- | --- | --- |
| The original key always shows (e.g. `hello`) | The language file wasn't loaded: wrong path, or the filename doesn't match `lang_final` | Confirm `config/lang-zh_CN.php` exists and that `lang_final` normalizes to `zh_CN` |
| All translations lost after upgrading an old project | The default of `lang_file_path` changed from `'lang/'` to `'lang-'`, so file locations don't line up | Rename files to `config/lang-zh_CN.php`, or set `'lang_file_path' => 'lang/'` to keep the old layout |
| A key written in a frag didn't take effect | When the main file and a frag collide on a key, **the main file wins** | Change that entry in the main file; frags only fill keys the main file lacks |
| Adding `?lang=zh_CN` to the URL has no effect | `lang_final` was already computed at init; changing `$_GET` at runtime won't re-detect | Set `$_GET['lang']` **early in the request** (e.g. `onPrepare`), or configure `'lang_final' => 'zh_CN'` directly |
| `{name}` wasn't replaced | That key **doesn't exist** in the language file, so it fell back to the original string | Confirm the key is in the language file; or pass a `$fallback` containing `{name}` |
| A child app's language differs from the main app's | `lang_follow_root` defaults to `true`; child apps are expected to follow the root | If you want a child app to detect independently, give it `'lang_follow_root' => false` |
| You want to take over translation completely (e.g. an external service) | No suitable hook point | Configure `'lang_handler' => function ($str, $args) { ... }` |
| Nested arrays in a language file (e.g. `'user' => ['login' => 'Login']`) | `Lang` only does **flat key** lookup; no dot-path support | Flatten the keys (`'user.login' => 'Login'`), or use `lang_handler` to parse them yourself |
